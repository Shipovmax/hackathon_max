## Твоя зона

Правишь: `backend/apps/bot/` целиком — обработчики, планировщик, уведомления, тексты, кнопки,
клиент MAX API, свои тесты в `backend/apps/bot/tests/`.

Не трогаешь: `backend/apps/core/` и `backend/apps/api/` (Толик), `frontend/` (Максим).

Понадобилось новое поле в моделях — пиши Толику, не добавляй сам: миграции ведёт он.

Ветка: `feature/bot`.

## Важно про токен

Бот работает на сервере и получает события через Long Polling. **С одним токеном работает
только один запущенный бот.** Перед локальной отладкой останови серверный:

```bash
ssh -i ~/.ssh/hackathon_vm ubuntu@130.193.35.250
cd ~/hackathon_max && docker compose stop bot
```

После отладки верни: `docker compose start bot`. Пока серверный бот работает, локальный
`run_bot` не запускай, иначе вы будете перехватывать события друг у друга.

## Задачи по порядку

Задачи Y1–Y4 ни от кого не зависят, начинай с них. Y5 и дальше требуют, чтобы Толик закрыл
свои T2 и T3 (`check_can_mark`, `mark_done`) — если их ещё нет, займись Y2–Y4.

### Y1. Разобраться с ботом на живых данных

Залей демо-данные и пройди сценарий привязки руками:

```bash
cd backend
python manage.py seed_demo --owner-max-id <свой MAX id>   # напечатает коды приглашения
python manage.py run_bot
```

В MAX: `/role` → «Я сотрудник» → отправь код → бот должен ответить «Готово. Вы подключены к
точке …». Это уже работает, задача — убедиться, что всё понятно, и найти шероховатости.

### Y2. Создание задач на день

`scheduler.generate_task_instances(now)` — создать `TaskInstance` на сегодня по активным
шаблонам всех точек: ежедневные каждый день, разовые в свою дату. Повторный запуск не должен
плодить дубли (в модели есть уникальность по шаблону и дате).

Планировщик тикает раз в 30 секунд (`run_scheduler`), поэтому каждая функция должна быть
безопасна при частом вызове: смотри на поля `*_sent_at` и статусы, чтобы не слать дважды.

### Y3. Начало смены

`scheduler.send_shift_start_messages(now)` — когда по опубликованному графику начинается
смена, отправить сотруднику список задач на сегодня.

Формат зафиксирован: «Смена началась. Ленина, 14 · до 17:00» и список «09:00 Открытие
магазина». Заготовка в `texts.shift_started`.

### Y4. Напоминание с кнопкой «Выполнено»

`scheduler.send_reminders(now)` — за `REMINDER_MINUTES_BEFORE` минут до планового времени
отправить всем, кто на смене, «Через 5 минут — открытие магазина» и кнопку «Выполнено»
(`keyboards.done_button`). Отметить в задаче, что напоминание отправлено.

### Y5. Нажатие «Выполнено»

`handlers/tasks.on_done(client, account, callback_id, instance_id)`:

1. найти сотрудника по аккаунту;
2. `check_can_mark` (функция Толика) — если нельзя, ответить заглушкой из `texts.denial_*`,
   объяснив причину и кто сделает это вместо него;
3. если задача требует фото — перевести в «ожидает фото», запомнить сотрудника и время,
   попросить фото;
4. если нет — `mark_done` и подтверждение со временем и следующей задачей.

### Y6. Приём фото

`handlers/tasks.on_photo(client, account, message)` — фото приходит вложением
`{"type": "image", "payload": {"photo_id", "token", "url"}}`. Скачай файл по `url`
(`client.download_file`, токен бота туда слать нельзя) и сохрани в `Completion.photo`.

Если фото не пришло за `PHOTO_WAIT_MINUTES`, задача возвращается в прежнее состояние —
это тоже планировщик. Состояние ожидания хранится в базе, а не в памяти процесса: бот может
перезапуститься между нажатием и фото.

### Y7. «Что осталось»

`handlers/tasks.on_status(client, account)` — список задач **текущей смены** сотрудника с
отметками. Если смены сейчас нет — соответствующая заглушка: выходной, смена не началась,
смена закончилась.

### Y8. Просрочка и уведомление владельцу

`scheduler.mark_overdue(now)` — задачи, у которых истекло плановое время плюс допуск и нет
отметки, переводим в `overdue` и один раз уведомляем владельца
(`notifications.notify_owner_overdue`). Повторных напоминаний о просрочке не шлём.

### Y9. Закрывающее уведомление

Если просроченную задачу всё-таки отметили — владельцу один раз уходит
`notifications.notify_owner_closed_late`: точка, задача, время, опоздание, кто отметил.
Для этого есть поле `closing_notified_at`.

### Y10. Итог смены

`scheduler.send_shift_summaries(now)` — в конце смены «Смена завершена. Выполнено 3 из 4».
Невыполненное перечисляем сотруднику, только если задача действительно числилась за ним:
упрекать за чужую задачу нельзя.

### Y11. Механика «Беру» (Should have)

Делай только после Y1–Y10. Сценарий в `CLAUDE.md`, раздел 6: вопрос в личку каждому из
смены, первый нажавший забирает задачу, остальным сообщаем кто, за 15 минут до срока
повторное сообщение, к сроку без исполнителя — владельцу «Задачу никто не взял».

## Как проверять

```bash
cd backend
python manage.py test apps.bot     # твои тесты
python manage.py test              # все тесты, перед push
```

Тесты пиши в `backend/apps/bot/tests/`. Пример, как подменять клиент MAX без сети, есть в
`tests/test_dispatch.py` (класс `RecordingClient`).

## Тон сообщений

Коротко, по делу, без восклицательных знаков. Отказ всегда объясняет причину и говорит, кто
сделает это вместо сотрудника. Все формулировки держи в `texts.py`, не разбрасывай по коду.
